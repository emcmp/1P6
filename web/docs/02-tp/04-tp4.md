# TP4 – Super RPG Infini : événements et combats

## 🎯 Objectif et projet de départ

**Continue le projet console C# du [TP3](03-tp3.md)**. Ce Bloc B ajoute un personnage, des événements et un combat au tour par tour. Il est évalué indépendamment sur **100 points** et se réalise en **exactement deux rencontres**. Utilise les variables, tableaux, fonctions, conditions, `switch` et boucles déjà vus. Aucune architecture orientée objet n'est exigée.

Réutilise la navigation, les visites et le chargement CSV du TP3 s'ils fonctionnent. **Conserve le traitement clé/porte/victoire du TP3 à un seul endroit** : le TP4 l'appelle ou s'y raccorde; il ne le réimplémente pas dans un second `switch`.

Si ton TP3 est incomplet, commence avec la grille 3 × 3 ci-dessous, les coordonnées du joueur et ton menu de déplacement validé. Fais approuver cette base minimale par le professeur; teste d'abord les événements en plaçant directement les coordonnées dans `Tests()`. La reprise du chargeur CSV n'est pas un nouveau critère du TP4. Adapte les noms à ton projet et garde une seule déclaration de chaque variable. La clé, la porte et la navigation doivent être raccordées pour l'essai final.

## Rencontre 14.1 — Personnage, équipement et événements

### Étape 1 — Initialiser le personnage et le sac

Comme dans l'ancien bloc d'événements, appelle `InitialiserPersonnage()` au démarrage, avant la navigation. Tu peux adapter le personnage et le sac du [TP2](02-tp2.md), ou utiliser cette initialisation simplifiée si ton TP2 n'est pas terminé :

```csharp
// À placer avec les autres variables du programme.
const int VIDE = -1;
const int EPEE = 0;
const int POTION = 1;
const int RATION = 2;

static string gNomPersonnage = "Ari";
static int gPV = 10;
static int gIntelligence = 10;
static int ennemiPV = 10;
static int[] gSacADos = { EPEE, POTION, RATION, VIDE, VIDE };
```

Ces indices correspondent aux trois premiers équipements du TP2. Si tes indices diffèrent, adapte les constantes. Le sac contient des **indices d'équipement**, et `VIDE` représente un emplacement libre. Aucun achat, calcul de poids ou reprise complète du TP2 n'est requis ici. `InitialiserPersonnage()` remet les PV et le contenu initial du sac au début d'une nouvelle partie.

Prévois trois petites fonctions à l'aide de boucles sur le tableau :

- `RechercherEquipementDansSac(int equipementRecherche)` retourne un booléen : vrai dès qu'une case contient cet indice, faux après le parcours sinon.
- `RetirerEquipementDansSac(int equipementRecherche)` remplace **une seule occurrence** par `VIDE`, puis retourne vrai; retourne faux si l'objet est absent.
- `AjouterEquipementDansSac(int equipement)` remplit le premier emplacement `VIDE`, puis retourne vrai; retourne faux si le sac est plein.

```pseudo
fonction RechercherEquipementDansSac(equipementRecherche)
    pour i de 0 à gSacADos.Length - 1
        si gSacADos[i] == equipementRecherche
            retourner vrai
    retourner faux
fin fonction
```

**Test rapide :** rechercher l'épée donne vrai. Retirer une potion libère une seule case; la rechercher ensuite donne faux si c'était la seule. Ajouter une ration remplit une case libre. Remplir tout le sac puis tenter un ajout donne faux sans écraser un objet.

### Étape 2 — Déclencher un événement en entrant dans une salle

Crée ou adapte `GererEvenements()`, avec un `switch` sur `donjon[positionLigne, positionColonne]`. Appelle-la **une fois après un déplacement réussi**, jamais après un choix invalide. La case de départ est vide. Exemple de carte de test :

```csharp
static string[,] donjon = new string[3, 3]
{
    { "", "🧪", "👺" },
    { "", "🍞", "🗝" },
    { "🚪", "", "" }
};
```

Si tu utilises le CSV du TP3, adapte son contenu avec les mêmes symboles et les mêmes virgules :

```csv
,🧪,👺
,🍞,🗝
🚪,,
```

| Case | Traitement requis |
|---|---|
| `🗝` et `🚪` | Laisser agir le traitement du TP3; vérifier son raccordement sans ajouter une autre règle de victoire |
| `🧪` | Essayer d'ajouter `POTION`; vider la case seulement si l'ajout réussit; sinon afficher « Sac plein » et conserver l'objet |
| `🍞` | Même traitement avec `RATION` |
| `👺` | Mettre `ennemiPV` à 10 et appeler `Combat()`; vider la case seulement si l'ennemi est vaincu |
| `""` | Aucun événement |
| Autre symbole | Décor sans effet; aucun combat implicite |

Le tableau `donjonVisite` sert à l'affichage; il ne suffit pas à mémoriser un objet ramassé. Modifie la case résolue dans `donjon` pour empêcher de recevoir plusieurs fois le même objet. Conserve toujours la porte.

```pseudo
fonction GererEvenements()
    evenement = donjon[positionLigne, positionColonne]
    selon evenement
        cas potion ou ration
            si AjouterEquipementDansSac(indice correspondant)
                vider la case courante
            sinon
                afficher "Sac plein"
        cas ennemi
            ennemiPV = 10
            Combat()
            si ennemiPV <= 0
                vider la case courante
        // clé et porte : conserver le raccordement unique du TP3
        // case vide ou décor : rien à faire
fin fonction
```

Pour cette première rencontre, `Combat()` peut simplement afficher « Début d'un combat contre un ennemi avec 10 points de vie ». Cette version provisoire ne tue pas l'ennemi et ne vide pas sa case.

**Tests rapides :** entrer sur une potion avec une place libre, sortir puis revenir : un seul ajout. Refaire avec un sac plein : objet toujours au sol. Entrer sur l'ennemi : un seul appel de `Combat()` par déplacement. Refaire l'essai porte sans clé, puis clé et porte, avec la logique du TP3.

## Rencontre 14.2 — Combat et fin de partie

### Étape 3 — Afficher le menu et résoudre une ronde

Remplace le message provisoire de `Combat()` par une boucle. Affiche les PV du personnage et de l'ennemi à chaque tour. Le menu propose :

| Choix | Effet requis |
|---|---|
| `A` — Attaquer | Infliger 3 dégâts, plus 3 si le sac contient l'épée, plus `gIntelligence / 5` (division entière) |
| `P` — Potion | Si présente, retirer une potion et gagner 5 PV |
| `R` — Ration | Si présente, retirer une ration et gagner 4 PV |

La valeur de base fixe de 3 remplace le jet de dé de l'ancien bloc pour faciliter les essais. Exemple : avec l'épée et 10 d'intelligence, une attaque inflige `3 + 3 + 10 / 5 = 8` dégâts. Sans épée, elle inflige 5 dégâts.

Une potion ou une ration absente et un choix invalide affichent un message, **sans consommer de tour ni provoquer de dégâts**. Tu peux masquer une option absente, mais valide quand même la saisie. Une consommation réussie utilise un tour. Aucun plafond de PV n'est requis.

Après une action valide, si l'ennemi est encore vivant, il inflige **3 dégâts**. Un ennemi vaincu ne riposte pas. Le combat s'arrête automatiquement dès qu'un des deux adversaires n'a plus de PV; il n'y a pas d'option permettant de quitter librement un combat actif dans le noyau requis.

```pseudo
fonction Combat()
    tant que gPV > 0 ET ennemiPV > 0
        MenuCombat() // afficher PV et options
        lire choix
        actionValide = faux
        selon choix
            cas A
                degatsJoueur = 3 + gIntelligence / 5
                si RechercherEquipementDansSac(EPEE)
                    degatsJoueur = degatsJoueur + 3
                ennemiPV = ennemiPV - degatsJoueur
                afficher les dégâts infligés
                actionValide = vrai
            cas P
                si RetirerEquipementDansSac(POTION)
                    gPV = gPV + 5
                    actionValide = vrai
                sinon afficher "Aucune potion"
            cas R
                si RetirerEquipementDansSac(RATION)
                    gPV = gPV + 4
                    actionValide = vrai
                sinon afficher "Aucune ration"
            défaut
                afficher "Choix invalide"
        si actionValide ET ennemiPV > 0
            gPV = gPV - 3
            afficher les dégâts reçus
    si gPV <= 0
        afficher "Défaite : vous n'avez plus de PV"
    sinon
        afficher "Ennemi vaincu"
fin fonction
```

Les fonctions de menu, d'attaque ou de ronde peuvent être séparées si cela t'aide, mais cette décomposition avancée n'est pas obligatoire. Garde du code lisible avec les fonctions déjà travaillées en cours.

### Étape 4 — Revenir à l'exploration ou terminer

Après le combat, revenir au donjon seulement si `gPV > 0`. En cas de défaite, terminer aussi la boucle de navigation : afficher la défaite une seule fois et ne plus demander de déplacement. Vaincre un ennemi termine **le combat**, pas le donjon. La victoire du jeu reste celle de la clé et de la porte du TP3. Après un déplacement réussi, conserver cet ordre : marquer la visite, collecter et effacer la clé si présente selon le TP3, appeler `GererEvenements()`, puis vérifier les PV. Si le personnage est mort, arrêter la navigation; sinon, appeler `FinDePartie()` et sortir de la navigation si elle retourne vrai. Un choix invalide ou une direction bloquée ne déclenche aucun événement.

## ✅ Critères d'acceptation et tests courts

Effectue les essais en réinitialisant les variables entre les scénarios dans `Tests()`, sans ajouter de bibliothèque de tests.

| Scénario | Résultat attendu |
|---|---|
| Potion au sol, sac libre, retour dans la même salle | Un seul ajout et case vidée |
| Ration au sol, sac plein | Message, contenu du sac inchangé et ration conservée au sol |
| Deux potions dans le sac, utiliser `P` | Une seule retirée; +5 PV puis −3 si l'ennemi vit encore |
| Pas de potion, saisir `P`, puis choix invalide | PV et sac inchangés; le combat continue |
| Joueur à 10 PV, intelligence 10, épée, ennemi à 10 PV; deux attaques | Ennemi à 2 PV puis vaincu; joueur à 7 PV; aucune seconde riposte |
| Même combat sans épée | Deux attaques de 5 dégâts; une seule riposte |
| Joueur à 3 PV, ennemi à 10 PV; une attaque avec épée | Ennemi à 2 PV; joueur à 0; défaite et arrêt de la navigation |
| Ennemi vaincu, quitter et revisiter sa salle | Aucun nouveau combat |
| Porte sans clé, puis clé et porte avec personnage vivant | Porte verrouillée puis victoire unique, selon le TP3 |

Remets le projet console complet, avec le CSV si utilisé, selon les modalités habituelles du cours à la séance 14.2. Vérifie qu'il compile et qu'un parcours complet est possible. Il n'est pas nécessaire de terminer les bonus pour obtenir 100 points.

## 🎭 Bonus — entièrement facultatifs, hors des 100 points

À entreprendre seulement après les deux rencontres si le noyau fonctionne. Aucun bonus n'est nécessaire pour la note maximale.

- **Affichage avancé**, inspiré de l'ancien bloc : dessiner les murs d'une salle et son contenu avec des boucles, puis afficher le personnage; garder l'affichage simple disponible. Ne modifie pas les règles du jeu pour l'affichage.
- **Fuite** : ajouter `F`, préciser une règle de réussite et conserver l'ennemi dans sa salle si le joueur fuit. Éviter de relancer immédiatement le même combat; permettre de quitter la salle avant un nouveau déclenchement.
- **Variantes** : plusieurs ennemis, oasis ou équipement défensif. Décrire et tester les règles ajoutées sans alourdir le noyau requis.
